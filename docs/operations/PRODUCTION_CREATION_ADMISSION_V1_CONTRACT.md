## Exact production purpose review

An existing independent Compatibility reviewer previews a finite scope and
confirms its exact SHA through the original trusted local maintenance boundary.
The current active principal and each Profile's independent capability are
verified again at confirmation. A Case reviewer grant alone is insufficient.

Inputs bind current approved Case/Fingerprint/Storyboard/Pattern/Compatibility
refs, the complete executing machine-source inventory and Commit, exact allowed
Profiles/Styles, News source intents, finite quantity, and real-model execution
permission. The scope never adds approved facts or expands supported Case IDs.

News additionally requires an existing `news_pattern_reviewer` decision on the
exact Pattern production purpose. The original Pattern Owner writes its own
independent receipt, then the Compatibility/Release Owner writes admission.
Partial persistence resumes the same operation. No old isolated receipt changes.
This new Human decision is the purpose extension; the original v1.2 definition
and its `allowed_purposes` remain retained structural source provenance, not a
claim that the old approval already permitted production.
The new derived Registry identifies the old definition's purposes separately
from its explicitly amended runtime purpose, bound to the reviewed scope SHA.

Both original Native News paths must have completed source/Human/XLSX/Receipt/
Closure/Ledger verification before production preview and confirmation. The
original qualification Owner re-verifies their full retained evidence and
produces a minimal, source-bound summary. An independent Human production
decision reviews that summary. The release carries the summary and evidence
hashes, not private Customer/Request/Task/Ledger/media artifacts. The production
Reader verifies the frozen Human publication and current structural graph;
it does not use a private isolated customer runtime as production Authority.
This is distinct from v1.2's retained-origin qualification Reader, which stays
unchanged for v1.2 consumers.

The initial **review candidate** permits at most five videos and one Native
dispatch per Business. Its production policy is versioned separately from
isolated policies v1/v2; their original bytes and 20/40 evidence remain history.
Five is a candidate first rollout ceiling, not Founder acceptance of production
throughput. The stage recommendations remain unchanged; a larger target is
blocked explicitly, never reduced or filled with another source/type.

The Founder subsequently authorized opening real model execution. The candidate
scope example records this as `real_model_execution_authorized=true`. That field
does not assert real-provider quality, which remains `not_validated`. No real
model calls are made by this implementation/verification delivery.

## Release and currentness

v1.3 is explicitly production-purpose. Pack/verify/stage/activate remain with the
original release Owner and original operation/control locks. Build requires a
clean, accurately committed full source tree and the exact Human admission ref.
The current live control head must still match at stage, activation and use.
The runtime configuration names an explicit control root and exact Profile set;
it is never inferred from a historic provenance path or selected by mtime.

The production admission has an append-only parent chain. A withdrawal advances
the head and fences new use. Replaying an old approval or activation cannot
revive a withdrawn scope. Withdrawing does not require reacquiring the withdrawn
source's production eligibility. Existing v1.0/v1.1/v1.2 readers and receipts
keep their original versions and byte identities.

Native Batch, styled and unstyled Mix, Novel and Repurpose Request writers use
the original business/source/permission locks and validate the admitted current
scope. Source SHA, active Release, compatibility decisions or scope changes
invalidate a prior check. Model execution permission is checked before Native
Request writes. Unknown provider results retain the original REC-01 recovery;
this contract adds no retry or Task/Review/Export/Ledger system.

## Historical proof and maintenance input boundaries

`historical_bundle_root` is a read-only resolver of the exact archived
activation, parent chain, manifest and structural bundle. Only sealed Native
Ledger reconstruction calls `bound_source_paths(..., historical=True)`.
Successor activation or current withdrawal does not rewrite or invalidate past
proof. The archived Reader returns a bundle path, not current eligibility;
generation, review, publishing and new exports still use the live runtime
fences. Corrupted or mismatched historical refs remain rejected.

Completed v1.3 News status/lifecycle readers also delegate to the original
sealed Ledger history. They require exact Native event kinds, the current
append-only Ledger head, independent Human evidence, publication bytes and
Receipt/Closure refs. This permits reading a completed predecessor after a
successor activation; it does not recover an unsealed export or approve another
write. The original export recovery path still validates live authority before
finishing its own missing seal. A verified Closure-before-seal interruption is
projected as `ledger_seal_pending`, never as complete; status can reach the
existing same-Task authenticated recovery command. Historical generation-state
projection reconstructs the original Fact/Pattern context, attempt, response,
result and Task binding. This read-only branch requires validated sealed
production history and is never used by generation/review/export writers.
Root and request paths are normalized before identity comparison. Legacy
terminal readers retain their versions.

The maintenance CLI reads `--news-validation-refs` as a JSON array containing
the two existing Native refs. It validates the ref shape/path, then delegates
full source/current qualification to the original Owner. The input is not a
new approval or a replacement for either Native result.

Style grouping follows the pinned v2 or production-1 policy's per-Request quantity
bound. A five-slot Style batch becomes K=2,2,1 with
stable original Slot IDs; a new policy version never makes K=5 a legal Native
Style Request. The original v1 group/Request identities and historical policy
files keep their bytes and interpretation. Retaining an old unsupported group
does not authorize a K>2 Native write or remap its historical admission.
